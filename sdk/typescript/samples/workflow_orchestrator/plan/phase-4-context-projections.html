Phase 4 · Bounded context projections

Make context transfer explicit. A workflow names typed artifacts and history continuity; the host validates provenance, audience, and hard size caps before inference.

Projection

context: {
  history: "fresh" | "all" | { last_n: number },
  fragments: [{ id, kind, audience, provenance, content, max_tokens }]
}

Implementation

  1. Add codex-rs/core/src/context/workflow_projection.rs implementing ContextualUserFragment.
  2. Permit only registered fragment kinds: mission brief, typed stage output, repository evidence, decision amendment, and review issue.
  3. Enforce per-fragment and total projection caps before constructing the child turn.
  4. Persist a manifest of fragment IDs, hashes, provenance, audience, and applied truncation; keep contents out of non-model evidence.
  5. Preserve continuity independently from validation mode: inline, all-history, last-N, and fresh are explicit workflow choices.

Exact existing surfaces

  • codex-rs/protocol/src/protocol.rs:509 — additional-context entries.
  • codex-rs/core/src/context/contextual_user_message.rs:24 — fragment registration.
  • codex-rs/core/src/agent/control/spawn.rs:499 — full/last-N history.
  • codex-rs/app-server-protocol/src/protocol/v2/turn.rs:71 — turn context input.

Proof

Integration tests reject unregistered, oversized, wrong-audience, and unprovenanced fragments. A fresh worker receives only its projection; a continuing worker retains selected history without transcript duplication. Every injected item stays below the repository's 10K-token ceiling.

Stop: context only. No routing, intent semantics, automatic summarization, or transcript rewrite.
