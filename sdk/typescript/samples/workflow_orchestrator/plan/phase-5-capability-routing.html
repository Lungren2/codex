Phase 5 · Host-owned capability routing

Workflows request a capability lane and thresholds, never an unconstrained model choice. The host resolves model plus reasoning effort from human-reviewed machine-local policy and records why.

Decision

routing.select({ lane, minimum, escalation_allowed }) → {
  invocation: { model, reasoning_effort, service_tier },
  reason, eligible_alternatives, escalation_path, policy_revision
}

Implementation

  1. Add codex-rs/core/src/workflow/routing.rs with lane request, immutable policy snapshot, and route evidence types.
  2. Load profiles from machine-local configuration; do not embed Luna/Terra/Sol scores in protocol or source defaults.
  3. Order selection by minimum capability, lane affinity, then cost as tie-breaker.
  4. Classify failures before escalation: capability failure may escalate; tool, permission, dependency, or repository failure may not.
  5. Persist selected invocation, rejected eligible alternatives, reason, escalation path, and policy revision in StageResult.

Exact existing surfaces

  • sdk/typescript/src/threadOptions.ts:9 — current thread-scoped model controls.
  • codex-rs/app-server-protocol/src/protocol/v2/turn.rs:71 — per-turn model and effort inputs.
  • codex-rs/core/src/session/turn_context.rs:111 — effective invocation settings.
  • sdk/typescript/samples/workflow_orchestrator/runtime.ts:14 — bootstrap's temporary fixed routing.

Proof

Route fixtures prove thresholds and lane affinity beat cost; cost breaks only equivalent choices. Capability rejection triggers the configured next invocation, while tool and environment failures preserve the route and return a non-capability terminal result.

Stop: no self-learning ledger, silent policy mutation, mid-turn model switching, or route choice from prompt prose.
