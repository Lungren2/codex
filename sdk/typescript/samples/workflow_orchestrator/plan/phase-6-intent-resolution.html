Phase 6 · Intent resolution

Defend the user's goal before planning without turning every task into a committee. One typed resolver is the default; independent skepticism and user interruption are explicit, evidence-backed transitions.

Contract

IntentResult {
  understood_goal, success_criteria, explicit_constraints,
  assumptions: [{ claim, confidence, source, material }],
  pushback, blocking_questions,
  transition: "proceed" | "proceed_with_assumptions" | "ask_user"
}

Implementation

  1. Add codex-rs/core/src/workflow/intent.rs with the contract and transition evaluator.
  2. Resolve intent in one worker using the original request plus bounded repository facts.
  3. Allow a separate skeptic only when product ambiguity, authority, data handling, or user-journey risk justifies independence.
  4. Ask at most three root-owned questions only when different answers materially change the outcome.
  5. Persist unanswered non-blocking assumptions in the mission brief and final decision narrative.

Exact existing surfaces

  • codex-rs/core/src/tools/handlers/request_user_input.rs:61 — root-thread ownership.
  • codex-rs/protocol/src/request_user_input.rs:1 — request/answer contract.
  • codex-rs/core/src/session/mod.rs:2501 — interactive request lifecycle.
  • codex-rs/core/src/context/internal_model_context.rs:78 — bounded internal context fragment.

Proof

Intent fixtures proceed through harmless uncertainty, expose assumptions, request an independent skeptic only for a configured material risk, and pause the root workflow for no more than three genuinely outcome-changing questions. A child worker cannot ask the user.

Stop: no mandatory advocate/skeptic/resolver fan-out, certainty theater, preference memory, or autonomous product decisions.
